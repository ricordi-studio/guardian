## 1. なぜ既存の機械検査で検出できなかったのか

### 結論
この事故は、Guardianの既存検査が見ていた「整合性」の種類と、実際に壊れた「境界」の種類が違っていたため検出できなかった。既存の中心原則は「同じ意味の値が2箇所にあるなら、そのずれを機械で検出する」というものだった。一方、今回の `pull.mjs` の事故では、問題は「同じ意味の値がずれた」ことではなく、正本リポジトリ内に存在するファイルのうち、どれが配布物で、どれがそのリポジトリ自身の現場固有物かという**集合の所属判定**が定義されていなかったことにある。

修正前の `pull.mjs` は実質的に「正本リポジトリに存在する → 配布対象である」という規則を持っていた。つまり「物理的に同じリポジトリにあること」を「意味的に同じ配布境界に属すること」と同一視していた。Guardian専用リポジトリが作られる前は、この仮定が事故として表面化しなかった。しかし専用リポジトリ化によって「他プロジェクトへ配るGuardian本体(A)」と「Guardian自身をこの現場で監査するためだけのファイル(B)」が同じリポジトリに共存するようになり、その瞬間、従来は不要だった「AとBを区別する契約」が必要になった。既存の `check.mjs` / `selfcheck.mjs` がこの分類を検査する契約を持っていなかったため、機械的には異常として認識できなかった。

### selfcheckが検出できなかった理由
`selfcheck.mjs` の役割は「検査自身が正しく赤くなることを、見本をわざと壊して確認する」ことである。検査対象となる契約自体に「配布物/現場固有物の境界」が存在しなければ、selfcheckはその欠落を発見できない。selfcheckは「存在する検査が壊れていないか」は検証できても、「必要なのにまだ存在していない検査は何か」を自動的に発見する仕組みではない。少なくとも今回与えられた資料からはそのような機構の存在は確認できない。

### Unknown
`check.mjs` が具体的にどの契約をどの順序で検査しているかは資料にないため、詳細は Unknown。

## 2. 一度きりの偶然か、一般化できるパターンか

### 結論: 一般化できる。
今回の本質は `pull.mjs` 固有のバグではなく、「構造変更によって、それまで暗黙に同一視できていたものが複数の意味領域に分かれたのに、その区別が契約として追加されなかった」というパターンである。これは `context.md` にある「構造を正したら、それまで要らなかった区別が要るようになる」という事故後の教訓と一致する。

### 一般化したパターン(次の条件が揃うと再発しやすい)
- **条件1**: 1つの物理領域(例: repository)に複数の意味領域(配布対象/開発専用/現場固有/生成物/作業記録)が共存する。物理的には同じディレクトリでも、ライフサイクルや所有者が異なる
- **条件2**: 処理対象を「列挙」で決めている。修正前 `pull.mjs` は「正本の全ファイル」を列挙し「例外だけ後から除く」という集合定義になっていた。この方式では、新しい種類のファイルが追加されたとき、その種類を知らない既存コードは自動的に対象へ含めてしまう
- **条件3**: 新しい構造変更で意味の種類が増える。今回なら「Guardianを別プロジェクト内で開発」→「Guardian専用repoでGuardian自身をGuardian監査」という変更により、「正本にあるファイル」という1分類では足りなくなった
- **条件4**: コピー先に同名だが意味の異なるファイルが存在する。今回の `guardian.config.json` はその典型 ── 正本側では「Guardian自身の現場設定」、配布先では「そのプロジェクト固有のGuardian設定」であり、意味が異なる。そのため通常の「同名ファイルの同期」は危険になる
- **条件5**: 検査が内容整合性だけを見て、所属・所有・流通範囲を見ていない。各ファイル単体の内容が正しくても「そのファイルがそこへ来てはいけない」という事故を検出できない

### より抽象化した名前
この事故は少なくとも次のように表現できる: **Implicit Scope Boundary Failure**、または **Physical Containment ≠ Semantic Membership**(同じ場所にあるから同じ種類だ、という暗黙前提の破綻)。

## 3. 機械で検出・防止する仕組み

**A. 配布対象を「除外リスト」ではなく「正の宣言」にする**
現在の修正は「全ファイル − 現場のもの = 配布物」。既知の事故には効くが、新しい現場固有ファイルが追加されたとき、そのパスを除外リストへ追加し忘れると再発する。より強い契約は「配布物として明示されたものだけ = 配布物」。概念上の `distribution-manifest` を1つ持ち、`pull.mjs` はその宣言からしかコピー対象を作れないようにする。重要なのはファイル形式ではなく、**列挙された全ファイルをデフォルト許可しない**ことである。

**B. 全パスの分類を「全域」にする**
Guardianリポジトリ内の管理対象パスについて `distributed / local / generated / ignored` などの分類を必須にし、`UNKNOWN PATH` が1つでも存在したら検査を赤にする。新しいファイルを追加した瞬間に「このファイルは何者か」を決めない限り先へ進めなくする。事故原因が「新しい意味の種類が増えたのに契約が増えなかった」ことなので、これは特に有効。

**C. コピー先側の「上書き禁止領域」を機械で持つ**
送信側だけでなく受信側にも「このパスは現場固有なので外部から上書きしてはならない」という契約を持たせる。`pull.mjs` はコピー直前に「source says distributable」AND「destination says replaceable」の両方を満たした場合だけ書き込む。これにより送信側の分類ミスがそのまま破壊につながることを防げる。ただし、現在のGuardianにそのような受信側分類を自然に置けるかは資料からは Unknown。

**D. `pull.mjs` 自体に境界事故の回帰テストを持たせる**
最小fixtureとして `source/{distributable-file, local-only-file}` と `destination/{distributable-file, local-only-file}` を作り、`pull.mjs` 実行後に distributed file は更新され、local-only file は絶対に変わらないことを決定論的に確認する。さらに「local-onlyの種類を1つ追加したケース」を検査できれば、固定された既知パスだけを覚えた実装かどうかも確認しやすい。ただし、このテストだけでは「まだ誰も想定していない新分類」を自動発見できない。そのためA/Bの契約と組み合わせる必要がある。

**E. 境界そのものを物理的に分ける**
最も強い設計は、配布元とGuardian自身の開発現場をファイルシステム上でも分離すること。すると配布処理は専用の配布領域だけを見ることができ「同居している異種ファイルを分類する」必要自体を減らせる。ただし、具体的にどの構成がGuardianに適切かは、与えられた資料だけでは決められないため Unknown。

## 4. 今回の固定除外リストに対する評価

今回追加された `guardian.config.json, docs, .guardian, .git, .github, node_modules` の固定除外は、実際に発生した事故を止めるための修正として妥当。ただし一般化された再発防止としては弱い。理由は「新しい『現場のもの』が追加されたとき、それを自動的には現場のものと判断できない」ため。

したがって、この事故からGuardianへ昇格させる候補原則は:

> 異なる意味領域が同じ物理領域に共存するとき、未知の所属をデフォルト許可してはならない。

よりGuardianらしく書くなら:「分類されていないものを配らない。Unknownを配布可能として扱わない。」

## 5. Finding候補

**Observation**: Guardianの正本を専用リポジトリへ分離したことで、同じrepo内に「配布物」と「Guardian自身の現場固有物」が共存するようになった。`pull.mjs` はrepo内の全ファイルを配布対象と仮定していたため、現場固有物を配布先へ持ち込もうとした。既存検査は「値の不一致」を監視していたが「ファイルの所属範囲」を表す契約を持っていなかった。

**Hypothesis**: LLMや人間による構造変更では、既存の物理境界が複数の意味境界へ分裂することがある。その際、新しく必要になった分類軸が機械契約へ昇格しなければ、従来正常だった「全部扱う」というコードが危険になる。

**Candidate deterministic rule**: 集合をまたぐ自動操作では、対象集合を暗黙の物理包含で決めない。対象資格を明示し、未分類は失敗させる。

**Counterexample / limitation**: すべてのファイルを明示分類する方式がGuardianの規模や運用に対して過剰かどうかは、この資料だけでは判断できない。また、どの粒度(ファイル、ディレクトリ、役割、manifest等)で分類するのが最も美しいかも Unknown。
