Round 0 の3案(`round0/claude.md` 自分自身の案を含む・`round0/gemini.md`・`round0/chatgpt.md`)全てについて、
見落とし・誤り・過剰一般化・検証不能箇所を指摘する。

---

## 対象: round0/claude.md(自分の案)

### Strong points
- check.mjsの「宣言と実装のずれを見る」モデルが「そもそも宣言が無い」領域には手が届かない、という
  診断は他の2者とも一致しており、的を外していない
- 既存の `onlyIn` 系検査を流用する提案は、新しい種類の器を増やさずに済む点でGuardianの流儀に合っている
- RULES 44条(門には双子を置く)を明示的に引いて、コピー実行側と網羅性確認側を分けたのは、
  ChatGPTの案C(受信側チェック)と独立に「二重の確認」に辿り着いた点で価値がある
- degitの初回導入経路には効かないことを、隠さずUnknownとして明記した

### Weak points
- 「onlyIn系検査を流用できる」と書いたが、**check.mjsの実装を実際に読んで確認していない**。
  ChatGPTのUnknown欄が正直に「check.mjsの全検査内容は資料にないためUnknown」としているのに対し、
  自分は根拠を示さないまま実現可能性を断定的に書いてしまっている

### Missing assumptions
- 分類を「トップレベルのパス単位」で行うと暗黙に仮定しているが、ChatGPTの条件4
  (`guardian.config.json` が正本側と配布先側で同名だが意味が違う)は、パス単位の分類だけでは
  本質的に解決しない問題を指摘している。自分の案は「配らない」ことしか保証せず、
  「同名で別の意味を持つファイルが将来増えたときにどうするか」には答えていない

### Possible false positives
- 「未分類のパスが増えたら赤」という設計は、gitignore対象の一時ファイルまで拾うと誤検出になり得ると
  自分でも書いたが、対策の具体案(トラッキング対象だけに絞る、等)までは詰めていない

### Possible false negatives
- 分類が「存在するかどうか」だけを見る設計なので、ChatGPTの条件4のような**意味の衝突**
  (同じパスが2つの役割を持つ)は検出できない。これは自分の案の中で最も弱い箇所

### Unnecessary complexity
- `guardian.config.json` に配布分類の宣言を持たせる案は、**Guardian自身が自分自身を監査する
  この現場でしか今のところ必要ない**問題を、通常の配布先(consumer project)にも新しい宣言項目として
  背負わせる可能性がある。`KIT === "."`(自己監査の現場)のときだけ効く形にすべきで、
  そこを明示していなかった

### Evidence required
- check.mjsの実装を実際に読み、`onlyIn`(またはそれに類する検査種)が「集合の網羅性」を
  表現できる形になっているかを確認する必要がある

## 対象: round0/gemini.md

### Strong points
- 「配布ロジックを実際にselfcheckのサンプル内で実行し、生成物に現場固有ファイルが
  含まれていないかをアサートする」というテスト設計は、除外リストの正しさそのものを検証する
  具体的な仕組みで、ChatGPTの案D(fixtureによる回帰テスト)と独立に近い結論に到達している
- 結論(スコープ外/一般化可能/allow-list化)は自分・ChatGPTと3者一致しており、
  この事故の核心についてはブレがない

### Weak points
- 分量が3者中もっとも少なく、**再発条件の具体化**(ChatGPTの条件1〜5のような)がほぼ無い。
  「一般化できる」と結論だけ書いており、どういう条件で再発するかの分析が薄い
- **degitによる初回導入経路の問題に一切触れていない。** これはcontext.mdが
  「この実験の対象外」と書いた上で存在自体は明示していた事実であり、
  Unknownとして触れることもできたはずだが、そもそも言及がない

### Missing assumptions
- 「selfcheck.mjsの中で実際の配布処理を実行してテストする」という提案は、
  現状の `pull.mjs` が `git clone` でネットワークにアクセスすることを前提にしている可能性がある。
  Guardian自身のMETHOD.mdは `selfcheck.mjs` を「鍵もネットも要らない」ものと位置づけており
  (README.mdの「入れ方」表・METHOD.md第2層の記述と整合)、もしこの前提が正しければ、
  Geminiの提案はGuardian自身の既存の設計原則と衝突する。この衝突にGemini自身は気づいていない

### Possible false positives / false negatives
- 記述が結論のみで具体的な検査ロジックまで踏み込んでいないため、この観点では評価できる材料が少ない
  (Evidence requiredとして扱う)

### Unnecessary complexity
- 特になし。むしろ3者中もっとも軽量な提案

### Evidence required
- `pull.mjs` の配布処理を selfcheck.mjs の中で安全に(ネットワークアクセスを模倣/回避して)
  再現できるかどうかの確認が必要。できないなら、この提案はそのままでは採用できない

## 対象: round0/chatgpt.md

### Strong points
- **条件4(同名だが意味の異なるファイル)は、自分・Geminiのどちらも指摘できていなかった、
  最も鋭い指摘。** `guardian.config.json` が正本側と配布先側で違う意味を持つ、という
  具体的な事実に基づいており、単なる一般論ではない
- 抽象化した名前(Implicit Scope Boundary Failure / Physical Containment ≠ Semantic Membership)は、
  この先似た事故が起きたときに「これは前に見た形だ」と気づくための語彙として有用
- 案C(受信側にも「上書き禁止」の契約を持たせる、送信側だけに頼らない)は、
  自分が引いたRULES 44条(門には双子を置く)の趣旨に、独立に到達している
- 案D(source/destinationの最小fixtureで回帰テストする)は、Guardian自身が既に持っている
  「selfcheckが見本をわざと壊して赤くなるか確認する」という手法とほぼ同型で、
  最も実装に近い具体性を持つ
- 「今回の固定除外リストは事故の再発防止としては妥当だが、一般化としては弱い」という評価は、
  過小評価でも過大評価でもなく妥当

### Weak points
- **5つの案(A〜E)を並べただけで、どれを最初にやるべきかの優先順位付けがない。**
  これはこのCouncil自身が `VISION.md` と `protocol/` を分けた理由(器を情報より先に固めない/
  実験で必要性が確認されるまで実装しない)と矛盾する方向の提案の仕方であり、皮肉なことに
  ChatGPT自身が最初に出したCouncilの完成形SPEC(VISION.md)と同じ「先に全部設計する」傾向が
  ここでも出ている
- **案E(配布元とGuardian自身の開発現場を物理的に分離する)は、直近の意思決定と正面から矛盾する。**
  依頼主は「正本が2つあった(別プロジェクトで開発 / GitHubが正本)」という事故を経て、
  **わざと1つのリポジトリに統合した**(2026-08-29)。案Eはこれを逆走する提案であり、
  ChatGPT自身がcontext.mdのその経緯を読んだ上でなお提案している以上、
  「なぜ統合したのか」という理由への配慮が欠けている

### Missing assumptions
- 案B(リポジトリ内の全パスを分類必須にする)は、分類の維持コストが将来的にどう増えるかについて
  Unknown止まりで、具体的な見積もりの試みがない

### Possible false positives
- 案B・案Dのいずれも、gitignore対象ファイルの扱いに触れていない(自分の案と同じ弱点)

### Possible false negatives
- 案D自身が「まだ誰も想定していない新分類を自動発見できない」と自己申告しており、
  ここは正直で評価できるが、裏を返せば案Dだけでは条件3(新しい意味の種類が増える)への
  対策にならない。案Bとの併用が前提になっている

### Unnecessary complexity
- 案A〜Eを一度に提示したことそのもの。**今この段階で必要なのは、次の1手が何かであって、
  完成形の選択肢一覧ではない**(このCouncilの `promotion.md` が想定している「反証を経て
  段階的に昇格させる」進め方とも噛み合わない)

### Evidence required
- 案C(受信側の上書き禁止契約)を実装する場合、既存の `install.mjs` / `guardian.config.json` の
  どこにその宣言を足すのが自然かは、実装を読まないと判断できない

## 3者を通じた所感(批判とは別に、記録しておく価値がある一致点)

3者とも独立に「除外リストではなく許可リスト(何を配るかを正で宣言する)」「未分類は失敗させる」
という同じ方向に到達した。これはRound 2(自己反証)を経ても崩れにくい、確度の高い収束だと考えられる。
一方で、**それをどの粒度で・どこに実装するか**(トップレベルパス単位か/全パスか/manifest形式か)は
3者で割れており、ここはまだ収束していない。
