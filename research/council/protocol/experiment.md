# 実験の組み立て方

**いま使う手順。手動で回す(2026-08-29時点、コード0行)。**

## 1実験の材料

`experiments/EXP-NNN/` を1つ作り、その下に:

| ファイル/フォルダ | 中身 |
|---|---|
| `question.md` | 3者全員に**一言一句同じ**問いを渡す。曖昧さを残さない |
| `context.md` | 3者全員に**同じ**背景資料を渡す(実装の抜粋・事故の記録・関連する既存の規則)。ここが揃っていないと、答えの違いが「モデルの違い」なのか「見た材料の違い」なのか区別できなくなる |
| `round0/` | 独立回答。`claude.md` / `chatgpt.md` / `gemini.md` |
| `round1/` | 相互批判。同じファイル名 |
| `round2/` | 自己反証。同じファイル名 |

## 最低限、記録しておくこと

VISION.mdの「Experiment Reproducibility」は将来の自動化向けの理想形だが、
**手動運用の今**は、`context.md` の末尾に以下だけ書いておけば足りる:

- 日付
- 参加した3者(名前だけでよい。バージョン番号までは今は追わない)
- 何を実験のきっかけにしたか(実在の事故か、仮説の検証か)

★バージョンやシステムプロンプトの厳密な記録は、**手動運用で本当に必要だと分かってから**足す
(VISION.md 6節「Experiment Reproducibility」参照。先に作らない)。

## 進行

1. `question.md` と `context.md` を書く
2. [debate.md](debate.md) の Round 0 の手順で、3者に**個別に**渡す(互いに見せない)
3. [debate.md](debate.md) の Round 1 の手順で、3者の回答を全員に見せて批判させる
4. [falsification.md](falsification.md) の手順で、自分の案を自分で壊させる
5. 人がここまでを読み、[promotion.md](promotion.md) に従って `findings/FIND-NNN.md` を書く

## この手順自体が壊れたら

Round 0 でAIが勝手に前提を補ったり、Round 1 で片方の回答に引っ張られすぎたり、
`context.md` が長すぎて参照箇所が3者でズレたりする ── それ自体が**Councilの最初の事故**である。
起きたら `findings/` にCouncil自身の事故として記録し、そこで初めて対策(フォーマット固定・匿名化・
要約の追加など)を検討する。**起きる前から対策を作らない。**
