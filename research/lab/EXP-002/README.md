# EXP-002 ── 構造の壊れは、どの重さから検出できるか

2026-08-29 の対話から。Council(EXP-001)が「Guardianの設計」を題材にしたのに対し、
こちらは **仕組みそのものを実地で測る**ための実験室。

## 測ること / 測らないこと

- **測らない**: 「AIが構造を壊すか」── `WHY.md` の194件で既に証明済み。再確認しない
- **測る**: **壊れている構造を検出できるか。そして【どの重さから】検出できるか**

この分け方により、壊す側を人が意図的に作ってよくなる(盲検である必要がなくなる)。
測っているのは**検出器**であって、壊す側ではない。

## 題材

`subject/` ── 注文の合計を出す小さな道具(3ファイル・約150行)。
`WHY.md` の事故カタログに実在する型の壊れを **6件**仕込んである。
どれも動くし、casual なレビューなら通る。答えは `ANSWER.md`(★回す前に読まない)。

## 階段(軽い方から)

| 段 | 体数 | 何を試すか | 仮説 |
|---|---|---|---|
| **0** | 0 | 問いを「**いま一から書くなら、こういう形になるか?**」に変えるだけ | 引かれる学習の層が変わる |
| **1** | 1 | 実装を渡し、**仕様書(何を満たすか)**を書かせる | 実装の形を捨てて要件へ遡れるか |
| **2** | 2 | 仕様書 → 実装を1つ書かせる → 元と比べる | 実装を挟むと差が具体になるか |
| **3** | 5 | 仕様書 → **実装を3つ**書かせる → 共通点を抽出 | **収束**が意見を測定に変えるか |

各段で D1〜D6 のうち何件を**場所と理由つきで**名指しできたかを数える。
**頭打ちになった所の1つ下が、その仕事に要る重さ**である。

## 同時に測れるもの(段3)

- **3つが互いに似て、元と違う** → 仕様書の粒度が良い(信号が出ている)
- **3つが元に似ている** → 粒度が細かすぎる(仕様書が実装を写している)
- **3つが互いに割れている** → 粒度が粗すぎる(要件を決めきれていない)

粒度は勘で合わせる値ではなく、**回すたびに信号が返る**。

## 記録

`runs/` に各段の生の出力を残す。結論だけでなく**出力そのもの**を残すこと
── 後で「なぜそう判定したか」を辿れなくなるため。
