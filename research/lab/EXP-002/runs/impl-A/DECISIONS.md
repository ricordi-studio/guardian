# ★要確認 9 件の判断

確認相手がいないため、実装者(impl-A)が決めた。
判断の基準は次の 3 つ。上にあるものが優先。

1. **仕様書に明文がある場合は仕様書に従う。** ★要確認は「§n に書いたが逆かもしれない」という
   形の問いが多く、その場合 §n が既に答えを出している。★要確認だけを見て §n と違う実装をすると
   仕様書が自己矛盾する。
2. **不変条件(§8)を壊さない方を選ぶ。** 特に §8.4「規則は 1 箇所」と §5 の検算式。
3. **「黙って間違う」より「うるさく止まる」を選ぶ。** 金額を扱うので、静かな 1 円ずれが最悪。

---

## 1. 小計は値引き前か、値引き後か → **値引き前**

- **どう決めたか**: §5 のとおり、小計は商品・食料品・送料の税抜金額の合計。割引はそこから引く別の数。
  `合計 = 小計 − 割引 + 消費税` が常に成り立つ。
- **なぜ**: 仕様書 §5 が明文で「値引きを差し引く**前**」と定めている。加えて §5 は
  「読んだ人がその場で検算できなければならない」と要求している。小計を値引き後にすると、
  §6.2 の割引行は「内訳の再掲」となり、レシート上の 4 つの数を素直に足し引きしても合計にならない。
  読み手が検算できる形は値引き前しかない。★要確認 1 が問題視している「割引が二重に見える」現象も、
  値引き前に統一することで消える。
- 実装: `src/calculate.js` の `subtotal` は `countsTowardSubtotal` が真の種別(商品・食料品・送料)
  だけを足す。割引は `discount` に絶対値で溜め、`total = subtotal - discount + tax` で 1 回だけ引く。

## 2. 割引の税戻しの丸めの向き → **絶対値の切り捨て(全種別一律)**

- **どう決めたか**: 丸め関数は `truncateTowardZero` ただ 1 本。正なら切り捨て、負なら 0 へ向けて切り上げ。
  割引専用の丸めは作らない。例: 割引 −105 円 → 税 −10.5 → **−10**。
- **なぜ**: §3.2 が「この規則は全種別に一律で適用され、種別によって向きが変わることはない」と
  明文で書いている。また §8.4 が「丸めは 1 箇所の規則だけ」と要求しており、
  割引にだけ別の丸め関数を置く現状の形は §8.4 違反そのもの。
  なお「利用者有利にならないように」という現状のコメントは、
  絶対値切り捨てでも満たされる(戻す税を小さい側に丸めるので、請求額は 1 円大きくなる)。
  意図は保たれるので、非対称な実装を残す理由がない。

## 3. 割引の税率 → **常に 10%**

- **どう決めたか**: 割引明細の税率は 10% 固定。値引き対象の税率には合わせない。
- **なぜ**: §3.1 の税率表が「割引 → 10%」と明文で定めている。★要確認 3 の懸念(食料品への値引きでも
  10% 戻る)は理解できるが、これを直すには入力に「この割引はどの明細に紐づくか」という情報が必要で、
  §2 の入力にはその情報が無い。**入力に無い情報を推測して規則を変えることはできない。**
  8% で戻すべき値引きは、種別を分ける(例: `discount_food`)か、割引に対象を持たせる
  入力仕様の変更が先。それは仕様書の §2 と §3.1 の両方を変える話なので、実装側の判断で先取りしない。
- 影響範囲は `src/kinds.js` の `discount.taxPercent` 1 箇所。将来 8% の値引きを足すときは
  種別を 1 つ増やすだけで済む形にしてある。

## 4. 送料無料の判定基準 → **商品と食料品の税抜金額のみ。割引も送料自身も含めない**

- **どう決めたか**: 基準額 = 商品の金額 + 食料品の金額。5,000 円**以上**(境界を含む)で無料。
  割引を引く前の額で判定し、送料自身は基準額に入れない。
- **なぜ**: §4 が「商品と食料品の金額の合計(税抜)が 5,000 円以上」と明文で定めており、
  送料も割引も列挙されていない。★要確認 4 が挙げる「値引き後で判定」は運用上ありうるが、
  §4 の本文と矛盾する。また値引き後判定を採ると、クーポンを使った瞬間に送料が復活して
  合計が跳ねるという説明しづらい挙動になる。明文どおりが安全。
- 送料自身を含めない点は、含めると「送料が高いほど送料が無料になりやすい」という
  自己参照的で不安定な規則になるため、明示的に除外した。
- 実装: 種別表の `countsTowardShippingFreeThreshold` フラグ 1 つで表現。判定は
  `src/calculate.js` の 1 箇所だけで行い、レシート経路も合計のみ経路も必ずそこを通る(§4 末尾, §8.4)。

## 5. 割引明細の税率注記 → **出す(`(税10%)`)**

- **どう決めたか**: 割引行にも他の明細と同じ形式で税率注記を出す。
  例: `割引 クーポン x1  -¥500 (税10%)`
- **なぜ**: 割引明細は実際に税額へ −50 円という寄与をしている。注記が無いと、
  レシートを読んだ人が消費税欄の数を自力で組み立てられない
  (§5 の「その場で検算できなければならない」に反する)。
  また §6.1 は「その明細に**適用された**税率を示す」と書いており、
  割引には 10% が適用されている以上、出すのが素直。
  注記を常に出すことで、行末が必ず注記で終わり「行末に余分な空白を残さない」も自然に守られる。

## 6. 定義されていない種別 → **エラーにして止める**

- **どう決めたか**: 未知の種別コードを見つけた時点で例外を投げる(`未定義の種別です: "gift"`)。
  無税の明細として黙って受け入れない。
- **なぜ**: 黙って通すと 2 つの事故が同時に起きる ──
  (a) 税額が 0 になり、請求額が静かに不足する。(b) §6.1 が禁じている「内部の種別コードがそのまま画面に出る」。
  どちらも表示上は正常に見えるため、誰も気づかないまま出荷される類の失敗。
  ★要確認 6 自身が「黙って通すのは事故のもと」と書いており、その判断に従った。
  新しい種別が必要になったら `src/kinds.js` の表に足す ── 税率・表示名・小計への算入・
  送料判定への算入を**全部**書かないと定義が完成しない形にしてあるので、足し忘れが起きない。

## 7. 丸めの位置 → **明細ごと**

- **どう決めたか**: 税は明細ごとに計算し、明細ごとに円へ丸めてから総和を取る。
  税率ごとの合算後 1 回丸めは採らない。
- **なぜ**: §3.2 が「明細ごとに計算し、明細ごとに円単位へ丸める(全明細の金額を合算してから
  一度だけ税を計算するのではない)」と、否定形まで添えて明文で定めている。
  ★要確認 7 の「実務上は税率ごとに 1 回」という方式は確かに存在するが、
  これは会計側の要求次第で変わる話で、実装者が推測で選ぶべきものではない。
  §3.2 の明文に従い、切り替えが必要になったときに 1 箇所(`src/calculate.js` の `lines` 生成)
  だけを直せばよい形にしてある。
- 差が出る例は test.js に残した(105 円の食料品 3 明細: 明細ごと 24 円 / 合算 25 円)。

## 8. 桁区切り → **入れない**

- **どう決めたか**: `¥12000`。カンマ等の区切り記号は使わない。
- **なぜ**: §6.1 が「桁区切り記号は使わない(例: `¥1000`)」と明文で定めている。
  §6.2 も「金額の表記規則は明細行と同じ」と縛っている。読みやすさの観点では区切りが欲しいが、
  それは表示要件の変更であって実装者の裁量ではない。
  なお区切りを入れると §6.2 の桁揃えの計算も変わるため、変えるなら両方まとめて変える必要がある。

## 9. 単価・数量が負・小数・0 の場合 → **入力検証を要件とする(0 は許可、それ以外は拒否)**

- **どう決めたか**:
  | 条件 | 扱い |
  |---|---|
  | 単価・数量が整数でない(小数・NaN・文字列) | エラー |
  | 数量が負 | エラー |
  | 商品・食料品・送料の単価が負 | エラー(値引きは種別 `discount` で表すよう促す) |
  | 割引の単価が正 | エラー |
  | 単価 0 / 数量 0 | **許可**(金額 0・税 0 の明細として通す) |
  | 名称が空 | エラー |
- **なぜ**:
  - **小数を拒む理由**: §8.5 が「表示される金額はすべて円単位の整数であり、小数が画面に出ることはない」と
    要求している。小数の単価を受け入れると、これを守れるかどうかが入力次第になる。
    入口で弾けば、以降のすべての金額が整数であることが構造的に保証される。
  - **負を拒む理由**: §2 の表が種別ごとに符号を定めている(商品・食料品・送料は正、割引は負)。
    商品を負の単価で入れることは「割引を別種別で表す」という設計を迂回する道で、
    これを許すと送料無料の判定基準(§4)に負の額が混じり、規則が 2 通りに見えるようになる。
  - **0 を許す理由**: 単価 0(おまけ)も数量 0(取り消した行)も業務上ふつうに起きる。
    §2 の符号の定めにも反しない(0 は正でも負でもない)。計算結果も 0 で安全。
  - **総じて**: 検証は「静かな間違い」を「うるさい停止」に変換する装置。金額を扱う道具では
    後者のほうが常に安い。§8.3 が明細 0 件を正常系と明記している一方、壊れた明細については
    何も書いていないので、止めるほうを選んだ。

## ★要確認に無いが、書かれていなかったので決めたこと

- **負の金額の表記**: `¥-500` ではなく **`-¥500`**。§6.2 の割引行が `-¥<割引>` の形なので、
  明細行もそれに揃えた(§6.1 は「負であることが読み取れる形」としか書いていない)。
- **合計欄の桁位置**: `¥` を表示 11 桁目に置く。これは §6.2 の例(`小計` + 空白 7 個 + `¥`、
  `消費税` + 空白 5 個 + `¥`)から逆算した値で、一番広いラベル「消費税」(表示幅 6)+ 5 で求めている。
  ラベルを増やしても崩れないよう、定数ではなくラベル一覧から計算している。
  負の行は符号 1 文字ぶん左へ食い込ませ、`¥` の桁を保つ。
- **入力の形**: `{ items: [...] }` と、明細の配列そのものの両方を受け取る。
  §2 は「明細の並びを持つ」としか書いておらず、器の形を定めていないため。
- **種別コード**: 内部は英字(`product` / `food` / `shipping` / `discount`)、
  画面に出るのは日本語の表示名だけ(§6.1)。
