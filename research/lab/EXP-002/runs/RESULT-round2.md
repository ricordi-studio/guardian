## 採点(基準は `SCORING-round2.md`・結果を見る前に固定済み)

### T1 仕様書は実装の形を継いだか → **継がなかった**

関数名・ファイル分割・`if` の連鎖が1つも無い。種別×税率は**表**、§8 は**不変条件**の列。
**階段は成立した。**

### T2 ★要確認は壊れの検出器になったか → **なった。しかも新しい問いを出した**

9件のうち、要確認1(小計は前か後か)・2(割引の丸め)・5・6・7 が、そのまま仕込んだ壊れの在り処。
**要確認3(割引の税率を対象に合わせるべきか。食料品8%への値引きでも10%で戻る)は、
私も段0も挙げていない。** 仕様書を書く行為が、読むだけでは出ない問いを出した。

### T3(当初) 収束は順位を付けるか → **測れなくなった。それ自体が発見**

仕様書が壊れを**先に直していた**(§4=D5 / §6.1=D6 / §3.2=D4 / §3.1=D1,D2)。
だから3実装が揃っても収束ではなく指示である。

> **仕様書を書く工程そのものが、決定をしてしまう。**
> 一貫していないコードから一貫した要件は書けない ── 書く過程で決めざるを得ない。

### T4 粒度の信号 → **良い**

| 測定 | 結果 |
|---|---|
| 3実装が互いに一致するか | **8例すべてで合計もレシート文字列も完全一致** |
| 元と違うか | **違う**(レシートの中身・小計の定義・種別名の表示) |

README の表で言う「**3つが互いに似て、元と違う**」= 粒度が良い。
仕様書は細かすぎず(元を再現していない)、粗すぎない(3体が割れていない)。

### T5 3体は1体より情報を足したか → **発見は足さない。信用を足す**

3体は**同じものを作った**:

| | A | B | C |
|---|---|---|---|
| 種別表を1枚に | `kinds.js` | `catalog.js` | `rules.js` |

★**明細の欄名まで3体一致した**(元は `{kind,title,price,qty}`。誰も元を見ていない)。

**割れたのは3つだけ**: 種別コードの大小文字(B=大文字 / A,C=小文字)、
容器の欄名(A=`items` / B,C=`lines`)、ファイル分割の細部。

> **収束は「構造」を発見しない ── 何が【必然】で何が【趣味】かを分ける。**
> 3体が同じにした所は常識が決めている。割れた所はどれでもよい。

## ★この回いちばん重い発見

**合計は、元と収束した3体で 8例すべて一致した。**

```
  同じ 2946 → 2946   /  同じ 5500 → 5500  /  同じ 6378 → 6378  … 8例すべて
```

**つまり、6つの構造の壊れは、振る舞いを1つも変えていない。**
どんな合計の試験を書いても、この壊れは永久に緑のまま通る。

だがレシート(人が見るもの)は違った:

```
元:          小計 ¥2700 − 割引 ¥300 + 税 ¥246 = 2646  ≠ 合計 ¥2946   ★300円合わない
収束した3体:  小計 ¥3000 − 割引 ¥300 + 税 ¥246 = 2946  = 合計 ¥2946   ✓
             coupon クーポン x1 ¥-300     ← 内部コードが露出(元)
             割引 クーポン x1 -¥300 (税10%) ← 収束
```

**元のレシートは、人が検算すると合わない。**構造の壊れ(割引の二重表現)が、
そのまま**人が読んで検算できない出力**になっていた ── 合計は正しいので、誰も気づかない。

## 「聞くべき2割」の自動抽出が働いた

3体とも、要確認3(割引の税率)を **「今の入力形式では実装不可能。入力仕様を変えられる人に上げるべき残件」**
として独立に同じ結論へ到達し、`DECISIONS.md` に残した。
B と C は要確認7(丸めの位置)も「会計側に確認すべき残件」として上げている。

> **3体一致 = 常識が決めている(聞かなくてよい)**
> **3体が「人に上げるべき」で一致 = 本当に聞くべきこと**

柿の例の「8割は聞かずに決まる / 2割は聞く」の切り分けが、**測定で出た。**
