# DECISIONS.md — 仕様書 §9「★要確認」9 件の判断

確認する相手がいないため、実装者(この実装の作者)が判断した。
形式は **項目番号 → どう決めたか → なぜ**。

判断の全体方針は 3 つ。

- **仕様書の本文(§1〜§8)が最優先。** §9 は「本文がこう書いてあるが本当か」という問いなので、
  本文を覆すだけの根拠が無い限り、本文どおりに実装する。
- **黙って通さない。** 判断がつかない入力は、間違った数字を出すより落とす。
- **規則は 1 箇所にしか置かない。** §8-4 を守るため、税率・閾値・丸め・表示名は
  `lib/rules.js` にだけ書き、他のファイルには数値を書かない。

---

## 1. 小計は値引き前か、値引き後か

**決定: 値引き前(§5 のとおり)。** `小計 = 商品 + 食料品 + 送料(有効なもの)の税抜金額`、
割引はその下の独立した行として引く。`合計 = 小計 − 割引 + 消費税` が常に成立する。

**なぜ:** §5 が「値引きを差し引く**前**」と明記し、`合計 = 小計 − 割引 + 消費税` を
不変条件として立てている。逆(小計=値引き後・割引行は内訳の再掲)を採ると、この式が
成立せず §5 と §6.2 を書き換えることになる。加えて §5 は「読んだ人がその場で検算できる」
ことを要件としており、値引き後の小計から更に割引行を引いて見せる形は
まさに §9-1 が問題として挙げた「割引が二重に見える」状態そのもの。
本文と不変条件の両方が同じ側を指しているので、迷う余地は無いと判断した。

実装: `lib/calculate.js` で `subtotal` は `rule.taxable` が真の明細だけを足し、
`discount` は割引明細の絶対値だけを足す。両者が混ざる場所は 1 つも無い。
`demo.js` で `total === subtotal - discount + tax` を毎回検算している。

---

## 2. 割引に対する税戻しの丸めの向き

**決定: 絶対値の切り捨て(0 に近づける向き)で全種別一律。** `Math.trunc` 1 本。
割引だけ別の丸め関数を使う、ということはしない。

**なぜ:** §3.2 が「この規則は全種別に一律で適用され、種別によって向きが変わることはない」と
明示的に念を押している。§9-2 が言う「利用者有利にならないように」というコメントは、
規則ではなく、あとから付いた説明に見える。種別ごとに丸めの向きが違う実装は、
新しい種別が増えるたびに「これはどちら向きか」を毎回考えることになり、
考え落としが 1 円のずれとして静かに残る。向きが 1 つなら考える必要が無い。

なお 1 円の有利・不利が本当に争点になるなら、それは丸めの向きではなく
「誰に有利か」の業務判断であり、仕様書本文に書かれるべき事柄だと考えた。
本文にその記述が無いので、書かれている規則(一律)を採った。

実装: `lib/rules.js` の `taxOf()` が唯一の丸め地点。
`Math.trunc((amount * taxNumer) / 100)` として、先に整数を掛けてから割る。
`amount * 0.1` のような浮動小数の掛け算を避け、`100 * 0.1 = 10.000000000000002` 系の
誤差が金額に入り込む経路を作らない。

---

## 3. 割引の税率は常に 10% でよいか

**決定: 常に 10%(§3.1 の表のとおり)。** 値引き対象の税率には合わせない。

**なぜ:** §3.1 の表が割引の税率を 10% と明記している。「値引き対象の税率に合わせる」を
採るには、入力に「この割引はどの明細に紐づくか」という情報が必要になるが、
§2 の明細が持つ情報は 種別・名称・単価・数量 の 4 つだけで、紐づけ先を表す情報が無い。
つまり対象税率に合わせる案は、**今の入力データでは実装できない**。
実装できない案を推測で補う(直前の明細に紐づける、等)のは、
仕様に無い規則を勝手に作ることになるので採らなかった。

これは業務上は実際に問題になり得る点(食料品への値引きで 10% 戻すと 2% 過大に戻る)なので、
本来は仕様書に「割引に対象を持たせるか」を追記して決着させるべき論点である、と記録しておく。

---

## 4. 送料無料の判定基準に割引を含めるか / 送料自身を含めるか

**決定: 商品・食料品の税抜金額の合計だけで判定する。割引は判定に影響させず、送料自身も含めない。**
閾値は 5,000 円で、ちょうど 5,000 円のときも無料。

**なぜ:** §4 が「**商品と食料品の金額の合計**(税抜)が **5,000 円以上**」と、
対象・税抜・境界の 3 つをすべて名指しで書いている。ここに割引や送料が入る余地は無い。
「送料を無料にするために送料自身を数える」のは循環しており、そもそも成り立たない。
割引後で判定する案は運用としてはあり得るが、それは §4 の書き換えを要する変更であり、
仕様書の本文に反して実装側で勝手に採る判断ではないと考えた。

実装: `lib/rules.js` の各種別に `freeShipBase` フラグを持たせ、
`lib/calculate.js` はそのフラグが真の明細だけを足す。
判定は `calculate()` の中に 1 度だけ現れ、レシート経路と合計のみ経路は
どちらもこの `calculate()` を呼ぶ。§4 末尾と §8-4 が要求する「2 経路で規則がずれない」は、
規則を 2 回書かないことで守っている(揃えるのではなく、分けない)。

無料になった送料は `calculate()` の中で明細の並びから落とす。
落とした後は表示にも小計にも税にも存在しないので、
「レシートには出ないが税だけ残っている」という取りこぼしが起きない。

---

## 5. 割引明細に税率注記を出すか

**決定: 出す(`(税10%)`)。**

**なぜ:** §6.1 は税率注記を「その明細に**適用された**税率を示す」と定義している。
割引明細には現に 10% が適用されて税額(負)が発生しているのだから、
定義に従えば注記が出るのが自然。注記を出さないと、レシート上の明細から
消費税欄の内訳を追えなくなる ── 消費税に負の 30 円が入っているのに、
その 30 円がどの行から来たのかがレシートを見ても分からない、という状態になる。
§5 の「読んだ人がその場で検算できなければならない」に照らして、出す側を採った。

---

## 6. 定義されていない種別の明細が来たときの扱い

**決定: エラーにする(例外を投げる)。無税の明細として黙って受け入れない。**

**なぜ:** §9-6 自身が「黙って通すのは事故のもと」と書いており、これには同意する。
より強い理由は §6.1 の「**4 種すべてに表示名が定義されていること**(内部の種別コードが
そのまま画面に出てはならない)」で、未定義の種別を受け入れると
表示名が無いので必ず内部コードが画面に出る ── つまり黙って通す実装は
§6.1 に違反せずには成立しない。受け入れる道は最初から塞がっている。

無税で通す案の実害は、金額が「エラーにならずに間違う」こと。
落ちれば気づくが、0 円の税で通れば誰も気づかないまま請求される。
気づける失敗の方を選んだ。

実装: `lib/calculate.js` の `validateLine()` が `isKnownKind()` で弾く。
種別を増やすときは `lib/rules.js` の `RULES` に 1 項足すだけでよく、
税率・表示名・注記・小計への算入・送料無料判定への算入がその 1 箇所に揃う。

## 7. 税の丸め位置(明細ごと / 税率ごとに合算して 1 回)

**決定: 明細ごとに丸める(§3.2 のとおり)。**

**なぜ:** §3.2 が「明細ごとに計算し、明細ごとに円単位へ丸める」「全明細の金額を合算してから
一度だけ税を計算するのではない」と、採らない方の案まで名指しで否定している。
ここまで書かれているものを実装側の判断でひっくり返す理由が無い。

ただし §9-7 の指摘は妥当で、これは会計・請求側の要求次第で変わる論点である。
そのため丸めの実装を `lib/rules.js` の `taxOf()` 1 箇所に閉じ込めた。
将来「税率ごとに合算して 1 回」へ変える場合に触るのは、集計側の 1 関数だけで済み、
レシート側・合計のみ側のどちらも書き換える必要が無い。
決定を変えやすい形にしておくことを、決定そのものの代わりにはしないが、備えとして残す。

---

## 8. 金額表記に桁区切りを入れるか

**決定: 入れない。`¥12000` と書く。負の額は `-¥500`。**

**なぜ:** §6.1 が「桁区切り記号は使わない(例: `¥1000`)」と例つきで明記している。
判断の余地は無い。

負の表現だけは §6.1 が「負であることが読み取れる形」としか書いていないので選択した。
`-¥500` を採ったのは、§6.2 の合計欄の割引行が `-¥<割引>` という形で示されており、
明細行と合計欄で負の書き方を揃えられるため。`¥-500` だと同じレシートの中に
2 通りの負の書き方が混在する。

## 9. 単価・数量が負(割引以外)、小数、0 の場合の扱い

**決定: 入力検証を要件とする。以下を満たさない注文は例外で落とす。**

| 項目 | 規則 |
|---|---|
| 種別 | 定義済みの 4 種のいずれか(項目 6) |
| 名称 | 空でない文字列 |
| 単価 | 円単位の整数(小数は不可) |
| 数量 | 整数、かつ 0 以上 |
| 単価の符号 | 割引は 0 以下、それ以外は 0 以上 |
| 0 | 単価 0・数量 0 は**許容**する |

**なぜ:**

- **小数を弾く理由:** §8-5 が「表示される金額はすべて円単位の整数であり、小数が画面に出ることはない」
  と定めている。単価に小数を許すと `単価 × 数量` が小数になり、この不変条件を
  出力の段階で守れなくなる。入口で弾けば、出口で守るための細工が要らない。
  併せて `lib/format.js` の `yen()` でも整数でなければ落とすようにし、
  万一検証をすり抜けても小数が画面に出るより先に止まるようにした(二重の網)。
- **符号を弾く理由:** §2 の表が種別ごとの金額の符号を規定している
  (商品・食料品・送料は正、割引は負)。負の単価を持つ「商品」は、
  仕様上どの種別でもない。それは割引として渡されるべきものなので、
  種別を間違えた入力として扱う。黙って受け入れると、
  §5 の「割引」欄に現れない値引きが小計にまぎれ、検算できないレシートになる。
- **0 を許す理由:** 数量 0 の明細も金額 0 の商品(おまけ等)も、
  仕様書のどの規則にも矛盾しない。金額 0・税 0 として素直に計算でき、
  検算も崩れない。矛盾しないものを禁止する根拠が無いので通す。
  ただしレシートには行として現れる ── 注文にその明細が存在した事実は残す方が正しいと考えた。

**この判断だけが §9 の中で唯一「仕様書本文に書かれていないことを足した」ものである。**
他の 8 件は本文の記述に従った結果だが、入力検証は本文が沈黙している領域なので、
実装者の判断で追加したことを明記しておく。緩める場合は `lib/calculate.js` の
`validateLine()` 1 関数を触れば済む。

## 補足: 判断の置き場所

| 判断 | 実装上の置き場所 |
|---|---|
| 1, 4 | `lib/calculate.js` の `calculate()`(集計と送料無料判定) |
| 2, 3, 5, 7 | `lib/rules.js`(税率・注記・丸め) |
| 6, 9 | `lib/calculate.js` の `validateLine()` |
| 8 | `lib/format.js` の `yen()` |

レシート経路(`buildReceipt`)と合計のみ経路(`calculateTotal`)は、
どちらも `calculate()` の戻り値だけを見る。
`lib/receipt.js` は金額の計算を一切行わない(書式だけを持つ)ため、
「レシートにだけあるバグ」「合計にだけ効く規則」は構造上生まれない。
