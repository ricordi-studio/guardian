# 第2回の採点基準(★結果を見る【前】に決めた)

結果を見てから基準を作ると、都合よく読めてしまう。先に固定する。

## 測る仮説

> **検出は軽い(段0で6/6)。重い段が要るのは【決定】── どれを直すか・どんな形にするか。**

## 段1(仕様書)で測ること

**T1. 仕様書は実装の形を継いだか**
- 継いだ兆候: 関数名・ファイル分割・`if` の連鎖・`kind` ごとの手続きが書かれている
- 継がなかった兆候: 種別 × 性質(税率・丸め・数えるか)が**表として**書かれている
- ★ここで継いでいたら、段3の実装は元を再現し、**この階段は成立しない**

**T2. 仕様書は「★要確認」に何を挙げたか**
- 段0が見つけた10件のうち、いくつが「要件か怪しい」として浮上したか
- ここに挙がるものは、**現状が壊れている証拠**である(要件なら迷わない)

## 段3(3実装)で測ること

**T3. 収束は順位を付けるか** ← 本命

段0が出した項目それぞれについて:

| 3実装のうち何体が回避したか | 意味 |
|---|---|
| **3/3** | **構造的必然**。直すべき。意見ではなく測定 |
| 2/3 | 有力だが、割れている |
| 1/3 | **趣味**。直さなくてよい可能性 |
| 0/3 | 段0の誤検出、または仕様書が要件として固定してしまった |

**これが出れば、「10件のうちどれから手を付けるか」が意見ではなく測定で決まる。**
仮説どおりなら、段0は順位を付けられず、段3は付けられる。

**T4. 粒度の信号**(README の表のとおり)
- 3つが互いに似て、元と違う → 粒度が良い
- 3つが元に似ている → 細かすぎ(仕様書が実装を写した)
- 3つが互いに割れている → 粗すぎ

**T5. 3体は1体より情報を足したか**
- 1体目だけを見た場合と、3体を見た場合で、言えることが変わるか
- 変わらないなら **段2(1実装)で足りる** ── 3体は無駄

## 反証条件(先に書く)

次のどれかが起きたら、仮説「重い段は決定に要る」は**支持されない**:

- 3実装が元と似ている(T4が「細かすぎ」)→ 階段が成立していない
- 3実装が完全に割れる(T4が「粗すぎ」)→ 順位が付かない
- 3/3で回避された項目が、段0の重要度の並びと**同じ**だった
  → **段0だけで順位も出ていた**ことになり、重い段は要らない

★最後の1つが、いちばん有り得る反証。段0は既に「1と3が最も危険」と順位らしきものを言っている。
**それと収束の結果が一致したら、段3の存在意義は薄い。**
