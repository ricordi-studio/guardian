# 注文計算・レシート出力 仕様書

この文書は「何を満たすか」だけを書く。実装の形(関数の分け方・ファイル構成・データ構造・
分岐の書き方)は一切規定しない。実装者が自由に決めてよい。

---

## 1. 目的

ひとつの注文を受け取り、次の 2 つを提供する。

- **レシート**: 人が読める 1 本のテキスト。
- **合計金額のみ**: 円単位の整数。プログラム(API など)から使われる。

同じ注文に対して、この 2 つが示す合計金額は **必ず一致すること**。
(片方だけに適用される規則、片方にしかないバグが存在してはならない。)

---

## 2. 入力

注文は **明細の並び** を持つ。並びの順序には意味があり、レシートの表示順はこの順序を保つ。

各明細が持つ情報:

| 情報 | 説明 |
|---|---|
| 種別 | 下記 4 種のいずれか |
| 名称 | 表示用の文字列(商品名など) |
| 単価 | 円 |
| 数量 | 個数 |

明細の **金額** は「単価 × 数量」と定める。

### 種別は次の 4 つ

| 種別 | 意味 | 金額の符号 |
|---|---|---|
| 商品 | 通常の商品 | 正 |
| 食料品 | 飲食料品(軽減税率の対象) | 正 |
| 送料 | 配送料 | 正 |
| 割引 | クーポン等の値引き | **負**(単価が負で与えられる) |

**入力として渡された注文データを、処理の過程で書き換えてはならない。**
(送料を除外する等の加工は、呼び出し側のデータに影響してはならない。)

---

## 3. 税の要件

### 3.1 税率

| 種別 | 税率 |
|---|---|
| 商品 | 10% |
| 食料品 | 8% |
| 送料 | 10% |
| 割引 | 10%(税を戻す。つまり税額は負になる) |

### 3.2 丸め

- 税額は **明細ごとに** 計算し、**明細ごとに円単位へ丸める**。
  (全明細の金額を合算してから一度だけ税を計算するのではない。)
- 丸めの向きは **絶対値の切り捨て**(= 0 に近づける向き)。
  正の税額は切り捨て、負の税額(割引の税戻し)は絶対値を切り捨てる。
  この規則は全種別に一律で適用され、種別によって向きが変わることはない。

### 3.3 税額の合計

注文全体の消費税額は、各明細の(丸め済みの)税額の総和とする。

---

## 4. 送料無料の要件

- **商品と食料品の金額の合計**(税抜)が **5,000 円以上** のとき、送料は無料になる。
  ちょうど 5,000 円のときも無料(境界を含む)。
- 無料になった場合、送料の明細は **注文から取り除かれたものとして扱う**。すなわち:
  - レシートに送料の行は表示されない。
  - 送料に対する税も課されない(税額にも合計にも一切寄与しない)。
- 判定に使う金額は税抜であり、税額は判定に含めない。
- この判定規則は、レシートを作る場合と合計金額だけを求める場合とで **同一** でなければならない。
  (2 つの経路で閾値や対象がずれてはならない。)

---

## 5. 金額の集計の要件

注文に対して、次の 4 つの金額が定まる。すべて円単位の整数。

| 名称 | 内容 |
|---|---|
| 小計 | 値引きを差し引く **前** の、課税対象となる明細(商品・食料品・送料)の金額の合計(税抜) |
| 割引 | 割引明細の金額の絶対値の合計(正の数として表す) |
| 消費税 | 3.3 の税額合計 |
| 合計 | 実際に請求する金額 |

次の関係が **必ず成り立つこと**:

```
合計 = 小計 − 割引 + 消費税
```

表示される 4 つの数は、読んだ人がその場で検算できなければならない。
一方が値引き後・他方が値引き前、という食い違いがあってはならない。

- 割引が 1 件も無い注文では、割引は 0 になる。
- 送料が無料になった注文では、送料は上記のどの数にも寄与しない。

---

## 6. レシート出力の要件

レシートは複数行のテキストで、次の順に並ぶ。

1. **明細行** — 注文の明細ごとに 1 行、入力の順序どおり。送料が無料になった場合は送料の行を出さない。
2. **区切り行** — 記号 `-` を 32 個並べた行。
3. **合計欄** — 下記の各行。

行と行は改行で連結する。末尾に余分な改行を付けない。

### 6.1 明細行

1 行に次を含む。

```
<種別名> <名称> x<数量>  ¥<金額> <税率注記>
```

- **種別名**: 種別ごとに定まった日本語の表示名。
  商品 → `商品` / 食料品 → `食料品` / 送料 → `送料` / 割引 → `割引`。
  **4 種すべてに表示名が定義されていること**(内部の種別コードがそのまま画面に出てはならない)。
- **数量**: `x` に続けて数量を書く。
- **金額**: `¥` を前置した円単位の整数。桁区切り記号は使わない(例: `¥1000`)。
  割引明細の金額は負なので、負であることが読み取れる形で表示する。
- **税率注記**: その明細に適用された税率を示す。商品・送料は `(税10%)`、食料品は `(税8%)`。
  割引の注記の扱いは §9 を参照。
- **行末に余分な空白を残さない。**

### 6.2 合計欄

次の行を上から順に出す。

```
小計       ¥<小計>
割引      -¥<割引>      ← 割引が 0 のときはこの行を出さない
消費税     ¥<消費税>
合計       ¥<合計>
```

- 割引の行は **割引が存在するときだけ** 表示し、値引きであることが分かる負の表現にする。
- 各行の金額は、**同じ桁位置から始まるように** ラベル側を空白で揃える
  (全角ラベルの幅を考慮し、金額の開始位置を一定にする)。
- 金額の表記規則は明細行と同じ(`¥` 前置・桁区切り無し・円単位の整数)。

---

## 7. 合計金額のみを求める経路の要件

- 入力は注文 1 件。出力は §5 の「合計」と等しい **数値**(文字列ではない)。
- §4 の送料無料判定を含め、レシートと同一の規則で計算される。
- この経路とレシート経路で結果が食い違わないこと(§1)。

---

## 8. 不変条件(実装がどうであれ守られること)

1. 同じ注文からは、常に同じ結果が得られる(外部状態に依存しない)。
2. 入力の注文データは変更されない。
3. 明細が 0 件の注文でも異常終了せず、小計・割引・消費税・合計がすべて 0 のレシートを返す。
4. 送料無料の判定・税率・丸め・閾値は、この文書に書かれた 1 箇所の規則だけであり、
   呼び出し経路ごとに別の規則が存在しない。
5. 表示される金額はすべて円単位の整数であり、小数が画面に出ることはない。

---

## 9. ★要確認

現状のコードを読んで気づいたが、**要件かどうか判断できなかった** 点。実装前に確定させたい。

1. **小計は値引き前か、値引き後か。**
   現状の実装は「小計」に割引を含めた後の値を入れつつ、その下に割引行を別途表示しており、
   `小計 − 割引 + 税 = 合計` が成立しない(割引が二重に見える)。
   本仕様書は §5 のとおり「小計は値引き前」で書いた。逆(小計は値引き後で、割引行は内訳の再掲)
   が正なら §5 と §6.2 を差し替える必要がある。

2. **割引に対する税戻しの丸めの向き。**
   現状は割引だけ他と逆向きの丸め関数を使っており、コメントには「利用者有利にならないように」とある。
   本仕様書は「絶対値の切り捨てで全種別一律」と解釈したが、
   「常に切り捨て(負の側に丸める)」が正なら割引の税額が 1 円ずれる。意図的な非対称か要確認。

3. **割引の税率が常に 10% でよいか。**
   食料品(8%)に対する値引きでも 10% で税が戻る。値引き対象の税率に合わせるべきではないか。

4. **送料無料の判定基準に割引を含めるか。**
   現状は商品・食料品の金額のみで判定し、割引は判定に影響しない。
   値引き後の金額で判定すべき、という運用ならば結果が変わる。
   また、判定基準に送料自身を含めない点も明示的に確認したい。

5. **割引明細に税率注記を出すか。**
   現状は割引行に注記が出ない。税を戻している以上 `(税10%)` を出すべきか、出さないのが正か。

6. **定義されていない種別の明細が来たときの扱い。**
   現状は税 0 として黙って通し、表示名も内部コードがそのまま出る。
   本来はエラーにすべきか、無税の明細として受け入れるべきか。黙って通すのは事故のもとなので要確認。

7. **税・金額を税抜の何に対して計算するかの丸め位置。**
   現状は明細ごとに税を丸めるが、実務上は税率ごとに合算してから 1 回だけ丸める方式もある。
   §3.2 は現状に合わせて「明細ごと」と書いた。請求・会計側の要求と一致するか要確認。

8. **金額表記に桁区切りを入れるか。**
   現状は `¥12000` のように区切り無し。表示要件として妥当か。

9. **単価・数量が負(割引以外)、小数、0 の場合の扱い。**
   現状は一切の検証が無く、そのまま計算される。入力検証を要件とするかどうか未定。
