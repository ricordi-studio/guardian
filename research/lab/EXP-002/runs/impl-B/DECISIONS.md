# DECISIONS.md — 仕様書 §9「★要確認」9 件の判断

確認する相手がいないため、実装者(この実装の作者)が判断した。
書式は **項目番号 → どう決めたか → なぜ**。判断が入っている場所(ファイル)も添える。

判断の共通方針:

- **仕様書本文(§1〜§8)が明示している事は、そのまま正とする。** §9 は「本文がこう書かれているが
  逆かもしれない」という問いなので、逆に倒すには本文を書き換えるだけの根拠が要る。ここでは
  本文を覆すだけの根拠が無いものは本文どおりにした。
- **本文が触れていない事(検証の有無・未定義種別の扱い)は、「黙って間違う」より「大きな音で止まる」を選ぶ。**
  合計金額は請求に直結するので、静かに 0 円として通す方が事故が大きい。

---

## 1. 小計は値引き前か、値引き後か

**決めたこと**: 小計は **値引き前**。割引は別枠の 1 行として引く。
`合計 = 小計 − 割引 + 消費税` が数字の上で成立する。
(`lib/compute.js` の `settle()`。割引明細は `countsInSubtotal: false`。)

**なぜ**: 仕様書 §5 が明示し、さらに「読んだ人がその場で検算できなければならない」と要求している。
現状の実装(小計に割引を含めた上で割引行も出す)は、その検算が合わない ── つまり §5 の要求そのものに
違反している状態なので、仕様書側が誤りである可能性は低いと見た。
また「小計は値引き後・割引行は内訳の再掲」を採ると、割引行の `-¥300` が引かれる数なのか
説明なのかが読み手に区別できず、§5 の「一方が値引き後・他方が値引き前という食い違い」を
かえって作り込むことになる。

---

## 2. 割引に対する税戻しの丸めの向き

**決めたこと**: **絶対値の切り捨て(0 に近づける向き)を全種別に一律**。
割引だけ別の丸め関数を使うことはしない。丸めは `lib/compute.js` の `roundTax()` の 1 箇所だけで、
`Math.trunc` を使う(`-10.5 → -10`)。

**なぜ**: 仕様書 §3.2 が「この規則は全種別に一律で適用され、種別によって向きが変わることはない」と
明示している。現状のコメント「利用者有利にならないように」は意図の説明としては筋が通るが、
それを採ると §3.2 の「一律」と §8.4 の「規則は 1 箇所だけ」の両方に違反し、
丸め関数が 2 つある状態が固定化する。
なお割引の税額 1 円は、絶対値切り捨てだと **店側が有利**(戻す税が 1 円小さい)になる方向であり、
「利用者有利にならないように」という元の意図とも矛盾しない。
1 円の非対称を意図的に入れる要求が後から出た場合は、`roundTax()` に種別を渡す形に変えれば
1 箇所の変更で済むようにしてある。

---

## 3. 割引の税率は常に 10% でよいか

**決めたこと**: **常に 10%**。(`lib/catalog.js` の `DISCOUNT.taxPercent`。)

**なぜ**: 仕様書 §3.1 が割引 10% と明示している。加えて **今の入力の形では他に決めようがない**:
明細(種別・名称・単価・数量)には「この割引がどの明細に掛かるか」を表す情報が無い。
値引き対象の税率に合わせるには、割引明細に対象の指定(対象明細への参照、あるいは対象税率そのもの)を
持たせる入力形式の変更が必要で、それは §2 の入力仕様の変更にあたる。
仕様書の範囲内で実装できる解は 10% 固定だけなので、そちらを採った。
**これは会計上ずれ得る点なので、入力形式を変えられる立場の人に上げるべき残件**として記録しておく。

---

## 4. 送料無料の判定基準に割引を含めるか / 送料自身を含めるか

**決めたこと**: 判定基準は **商品と食料品の金額(税抜)の合計だけ**。
**割引は含めない。送料自身も含めない。** 閾値は 5,000 円で境界を含む(5,000 円ちょうどは無料)。
(`lib/compute.js` の `isShippingFree()` と `FREE_SHIPPING_THRESHOLD` の 1 箇所のみ。
対象かどうかは `lib/catalog.js` の `countsInFreeShipping` が唯一の根拠。)

**なぜ**: 仕様書 §4 が「商品と食料品の金額の合計」「判定に使う金額は税抜」と明示しており、
現状の実装ともここは一致している(仕様書と実装が食い違っていない = 疑う根拠が弱い)。
「送料自身を含めない」は、含めると **送料を上げれば送料が無料になる** という自己矛盾した挙動になるので、
そもそも成立しない。
「値引き後で判定する」は運用としてはあり得るが、その場合クーポンを使うと送料が復活し、
値引きしたのに支払額が増える(300 円引いて 800 円の送料が乗る)注文が生じる。
利用者に説明できない挙動なので、明示の要求が無い限り採らない。

---

## 5. 割引明細に税率注記を出すか

**決めたこと**: **出す**(`割引 クーポン x1  -¥300 (税10%)`)。
(`lib/render.js` の `taxNote()`。種別によらず、その明細に適用された税率をそのまま書く。)

**なぜ**: §6.1 は税率注記を「その明細に適用された税率を示す」と定義しており、割引にも
実際に 10% が適用されて税額 −30 円が発生している。注記を出さないと、消費税の行の数字を
明細から検算しようとした人が 30 円を再現できない(§5「その場で検算できなければならない」)。
また、割引だけ注記を落とすと「注記のある行/無い行」の分岐が表示側に増え、
行末の余分な空白を作りやすい(§6.1 末尾の要求)。分岐を作らない形の方が壊れにくい。

---

## 6. 定義されていない種別の明細が来たときの扱い

**決めたこと**: **例外にして止める**(`OrderError`)。税 0 で黙って通すことはしない。
受け付ける綴りは内部コード(`PRODUCT` / `FOOD` / `SHIPPING` / `DISCOUNT`)と
日本語表示名(`商品` / `食料品` / `送料` / `割引`)の両方。(`lib/validate.js` / `lib/catalog.js`。)

**なぜ**: 仕様書自身が「黙って通すのは事故のもと」と書いているとおり、
税 0 で通すと **請求金額が静かに少なくなる** ── 失敗が誰にも見えないまま金額に出る。
さらに現状は表示名が無いので内部コードが画面に出てしまい、§6.1 の
「内部の種別コードがそのまま画面に出てはならない」にも触れる。
止めれば呼び出し側が必ず気づき、種別を足す判断が人間の側に戻る。

---

## 7. 税の丸め位置(明細ごと / 税率ごとに合算して 1 回)

**決めたこと**: **明細ごとに丸める**。(`lib/compute.js` の `taxOf()`。丸めが起きる箇所はここだけ。)

**なぜ**: 仕様書 §3.2 が「明細ごとに」「全明細の金額を合算してから一度だけ税を計算するのではない」と
二重に明示している。現状の実装とも一致しており、覆す根拠が無い。
税率ごとに 1 回だけ丸める方式(適格請求書で認められている方式)は会計側の要求として
あり得るが、それは計算結果が変わる仕様変更であり、実装者が黙って選べる範囲ではない。
`taxOf()` を 1 箇所に閉じてあるので、要求が確定したときの変更点は明確にしてある。
**会計側に確認すべき残件**として記録する。

---

## 8. 金額表記に桁区切りを入れるか

**決めたこと**: **入れない**(`¥12000`)。(`lib/render.js` の `money()`。)

**なぜ**: 仕様書 §6.1 が「桁区切り記号は使わない(例: `¥1000`)」と例つきで明示しており、
現状の実装とも一致している。加えて §6.2 は金額の開始位置を揃えることを要求しているので、
桁区切りを入れると桁数によって幅が変わり、揃えの規則が複雑になる。
表示上の好みで変えるなら `money()` の 1 箇所だけを直せば両方の経路に効く形にしてある。

---

## 9. 単価・数量が負(割引以外)、小数、0 の場合の扱い

**決めたこと**: **入口で検証し、違反は例外(`OrderError`)にする。** 具体的には:

| 条件 | 扱い |
|---|---|
| 単価が整数でない(小数) | 例外 |
| 数量が整数でない、または負 | 例外 |
| 割引以外の単価が負 | 例外(値引きは種別 `DISCOUNT` で表す) |
| 割引の単価が正 | 例外 |
| 単価 0 / 数量 0 | **通す**(金額 0・税 0 の明細としてレシートに出る) |
| 名称が空文字・文字列でない | 例外 |

(`lib/validate.js`。)

**なぜ**:

- **小数を止める**理由は §8.5「表示される金額はすべて円単位の整数であり、小数が画面に出ることはない」。
  小数の単価を受けると金額も小計も小数になり、画面に出るか、どこかで黙って丸められる。
  入口で止めるのが、丸めの規則を §3.2 の 1 箇所に保つ唯一の方法。
- **割引以外の負の単価を止める**理由は §2 の表が「割引だけが負」と符号を定めているから。
  商品を負の単価で入れる経路を許すと、割引行を出さずに値引きができてしまい、
  §5 の `合計 = 小計 − 割引 + 消費税` は成立したまま **割引が 0 と表示される**
  (検算できるのに嘘、という一番たちの悪い形)。
- **負の数量を止める**理由も同じ(数量 −1 は返品であって、この仕様書には返品の要件が無い)。
- **0 を通す**理由は、0 が「事故」ではなく普通に起こり得る値だから(在庫 0、無料の同梱品、
  100% クーポンの残額 0)。§8.3 が明細 0 件を正常終了と定めていることとも整合する。
  金額 0・税 0 として計算すれば、どの不変条件も壊れない。
- 検証は `readOrder()` の 1 箇所で行い、レシート経路も合計経路も必ずここを通る(§8.4)。

---

## 判断の外に置いた事(実装の自由として決めた事)

仕様書が規定していないので、要確認 9 件とは別に決めた事。

- **構成**: `index.js`(公開する入口 2 つ)/ `lib/catalog.js`(種別の事実)/
  `lib/validate.js`(入力の読み取りと検証)/ `lib/compute.js`(計算)/ `lib/render.js`(表示)。
  **計算は `settle()` 1 本だけ**で、`buildReceipt()` も `calculateTotal()` も必ずそこを通る(§1 / §7 / §8.4)。
  表示側は数を作らない(§8.4 の「経路ごとに別の規則が存在しない」を、構造で守る)。
- **入力の形**: 明細の配列そのもの、`{lines:[...]}`、`{items:[...]}` のいずれも受ける。
  明細の項目名は `kind` / `name` / `unitPrice` / `quantity`。
- **入力を書き換えない**方法: 検証時に自分用の明細を新しく作り、送料の除外もその複製の側で行う
  (§2 / §8.2)。返す結果は `Object.freeze` してある。
- **負の金額の表記**: 明細行も合計欄も `-¥300` の形(`¥-300` ではない)。§6.1 の
  「負であることが読み取れる形」と §6.2 の割引行の例(`-¥<割引>`)を同じ規則で満たす。
- **合計欄の桁揃え**: 全角を 2 桁と数え、`¥` の開始桁を 11 に固定する(`AMOUNT_COLUMN`)。
  負号は `¥` の直前に置き、その分だけ空白を 1 つ減らす。
