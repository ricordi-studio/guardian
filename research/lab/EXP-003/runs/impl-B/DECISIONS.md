# DECISIONS — 仕様書の「★要確認」への判断

確認する相手がいないため、実装者(私)が判断した。
以下は **項目 → どう決めたか → なぜ** の形で残す。

判断の共通方針:
1. 仕様書の本文に明示があるものは、本文を優先する(★要確認は本文の言い換えではなく、本文と矛盾しない範囲で決める)。
2. 本道具が「推測してはならない」と書かれている領域(一時的か恒久的かの判定)には踏み込まない。
3. 迷ったら **安全側** = 二重送信をしない / 成功と誤認しない / 事実と異なる報告をしない、を選ぶ。
4. どちらの運用もありうるものは、**既定値で仕様書どおりに振る舞い、値で切り替えられる**ようにする(§9 の「調整値は外から見え、変更できる」に沿う)。

---

## A. 1 回あたりの上限が数えるもの

**どう決めたか** — 「処理を試みた件数(= その回で決着がついた項目数)」を数える。成功・失敗にかかわらず 1 件と数える。`maxPerRun`(既定 50)。

**なぜ** — 仕様書 §3 の本文が「上限は『処理を試みた項目数』に対して掛かる。成功・失敗にかかわらず、決着がついた項目を 1 件と数える」と明記しており、★要確認 A はその再確認にすぎない。加えて「成功件数」を上限にすると、失敗が続く回で上限に到達できず、1 回の実行が事実上無制限に外部サービスを叩き続ける(全項目が失敗するとき終わらない)。上限の目的は「1 回の実行の重さを抑える」ことなので、失敗も重さとして数えるのが筋。
実装: `queue.js` の `run()` で `attempted` を決着ごとに +1。

## B. 諦めた項目の扱い(次回の自動実行で拾うか)

**どう決めたか** — 拾わない。諦めた項目は決着済みとして `cursor` を通過させ、自動実行では二度と送らない。回収は §8 の手動再試行だけ。

**なぜ** — §5 の不変条件が「一度決着がついた項目(成功・恒久的失敗・再送上限到達のいずれか)は、次回の実行で自動的に再送されてはならない」と明示している。自動で拾い直すと、外部サービスが落ちている間ずっと同じ項目を叩き続け、後続の項目が永久に進まない(先頭で詰まる)。手動再試行を別立てにしてあるのは、まさに回収を人の判断に委ねる設計だと読んだ。
実装: 失敗時も `state.cursor += 1`。`demo.js` の「3 回目の実行」で、送信手段が 1 度も呼ばれないことを確認している。

## C. 手動再試行の試行回数

**どう決めたか** — 既定では通常の実行と同じ回数(`maxAttempts`、既定 3)。ただし `retryMaxAttempts` を指定すれば手動再試行だけ厚くできる(既定 `null` = 同じ)。

**なぜ** — §8 本文が「通常の実行と同じ規則に従う」と書いているので、**既定は同じ**にするのが仕様書に忠実。一方で「手動再試行だけ厚くしたい」という運用意図は現実的にありうる(運用者が復旧を確認してから叩く場面)。§9 が調整値を外から変更可能にせよと言っているので、既定=仕様書どおり・必要なら値で変更、という形にした。3 と 5 のようにコード内に固定の差を埋め込むことはしない。
実装: `defaults.js` の `resolveConfig(options, isManualRetry)`。

## D. 手動再試行と恒久的失敗

**どう決めたか** — 対象から外さない。恒久的失敗で諦めた項目も手動再試行では 1 回だけ送信手段に渡し、その回の判定に従う(また恒久的なら 1 回で諦める)。

**なぜ** — §8 が「対象は、進捗情報に記録された『諦めた項目』だけ」と書いており、諦めた理由による選別は書かれていない。かつ §2.2 が「一時的か恒久的かの判定は送信手段が下す。本道具が中身を見て推測してはならない」と定めている。「恒久的だったのだから今も通らない」は本道具側の推測であり、この禁止に触れる。実際、運用者が外部サービス側の設定を直してから手で叩く場面では、以前の恒久的失敗が今回は通ることがある。
安全側の担保として、恒久的失敗は再試行時も **§4.2 の規則どおり 1 回で諦める**(待機もしない)ので、無駄な叩き続けにはならない。
実装: `retryFailed()` は理由で絞り込まず、`settleItem()` が §4 の規則を適用する。

## E. 待機時間の形(一定か指数的後退か)

**どう決めたか** — 既定は一定間隔(`retryDelayMs` 既定 1000ms、`backoffFactor` 既定 1)。`backoffFactor` を 1 より大きくすると指数的後退になり、`maxRetryDelayMs`(既定 30000ms)で頭打ちにする。

**なぜ** — §4.1 の要件は「待機時間を置くこと。連続で叩き続けてはならない」だけで、形は指定していない。仕様書は現状が一定間隔だと述べているので、**既定を変えて挙動を勝手に変更しない**方が安全(既定値の変更は目に見えない仕様変更になる)。一方、混雑起因の一時的失敗には後退が有効なので、選べる形にした。上限を設けたのは、後退が暴走して 1 回の実行が事実上止まるのを防ぐため。
実装: `attempt.js` の `delayFor()`。

## F. 例外の分類

**どう決めたか** — 例外は一律で一時的な失敗として扱う。例外の型・メッセージによる恒久/一時の振り分けは行わない。

**なぜ** — §4.3 が「例外は一時的な失敗として扱う」と本文で明示している。加えて §2.2 の「一時的か恒久的かの判定は送信手段が下す。本道具が中身を見て推測してはならない」に真正面から従うなら、本道具が例外の中身を見て「これは恒久的だ」と決めるのは越権。恒久的だと分かっているなら、送信手段が例外ではなく `{ ok:false, retryable:false }` を返すべきであり、その責務境界を崩さない。
例外の内容は `Error.name` と `message` を失敗理由に残す(§4.3 後段)。
実装: `outcome.js` の `fromThrown()`。

## G. 「残り件数」の定義

**どう決めたか** — 残り = **まだ一度も処理を試みていない項目の数**(`items.length - cursor`)。諦めた項目は含めない。諦めた件数は別のフィールド(`failed` / `failedTotal` / `failures`)で報告する。

**なぜ** — §6 本文が「『残り件数』は、まだ一度も処理を試みていない項目の数である。諦めた項目を残りに数え直してはならない」と明記している。混ぜると、B の判断(諦めた項目は自動実行で拾わない)と矛盾する数字になる ── 「残り 3 件」なのに次回の実行が 0 件しか処理しない、という嘘の報告になってしまう。**報告の数字は次に起きることと一致していなければならない**、という理由でこの定義を採る。

## H. 成功した項目の識別値一覧の用途

**どう決めたか** — 件数だけでなく識別値の集合を保持する。重複は積み上げない。

**なぜ** — §5 の要件 2 が「成功した項目の識別値の集合を保持する」と明示しているので、これは要件として実装する。実用上も必要になった: §8 の手動再試行で「成功した項目は諦めた集合から取り除き、成功の記録へ移す」を満たすには、識別値単位で移動先を持っていないと表現できない(件数だけでは移動が記録できない)。また、呼び出し側が外部サービス側の記録と突き合わせるときの根拠になる。

## I. 並びの同一性(再開位置を位置基準にするか識別値基準にするか)

**どう決めたか** — 再開位置は **位置(index)基準** の `cursor` にする。加えて、`run()` の入口で並びの識別値が一意であることを検証し、重複があれば送信を 1 件も始める前に例外にする。

**なぜ** — §5 末尾が「進捗情報は、渡された並びの内容が実行間で変わらないことを前提としてよい」と明示的に許している。位置基準は実装が単純で、「飛ばさない」「巻き戻らない」の不変条件を 1 つの単調増加する数で保証できる(証明しやすい = 事故が起きにくい)。識別値基準にすると、決着済み集合と並びの突き合わせが毎回必要になり、集合が肥大化する。
ただし前提が崩れたときに **黙って壊れない** ようにはした:
- 識別値が取れない / 重複している並びは、入口で `TypeError`(呼び出し側の誤りであり、送信中の異常ではないため §9 の「例外を漏らさない」の対象外と整理した)。
- 手動再試行は識別値で並びを引き直すため、該当項目が見つからなければ「並びの中に該当する項目が見つからないため再試行できなかった」という理由で失敗として残す(黙って成功扱いにしない)。

## ★要確認 以外に、書かれていなかったので決めたこと

- **進捗情報を書き換えるか** → 書き換えない。`run()` / `retryFailed()` は渡された進捗を複製し、新しい進捗を戻り値の `progress` に入れる。理由: 呼び出し側が保存する対象なので、途中で失敗した実行が呼び出し側の手元の進捗を壊さない方が安全。
- **進捗の形** → `{ version, cursor, succeeded[], failed[{id,reason}] }` の素の JSON。理由: §5 が「呼び出し側はこれを保存し、次回の実行に渡す」と言っているので、そのまま保存できる形でなければならない(Set や Map は JSON にできない)。`demo.js` で JSON 往復を確認している。
- **識別値の同一性判定** → 文字列化して比較する(数値 `1` と文字列 `"1"` は同じ項目とみなす)。理由: JSON 保存を往復した進捗と、生の並びの識別値の型がずれる運用がありうるため。
- **完了の報告** → `allSettled`(全件決着)と `clean`(全件決着かつ失敗ゼロ)を別々に返し、`isComplete()` / `isCleanlyComplete()` も分けた。理由: §7 が「『全件処理済み』と『失敗ゼロ』は別の概念として扱える」ことを求めているため。
- **解釈できない結果の理由文** → 「送信手段が解釈できない結果を返した (…)」と、何が返ってきたかを含める。理由: §4.5 の「実際に起きたことを表す」を満たすため。原因が送信手段側にあることが読んで分かる必要がある。
- **`ok:false` だが `retryable` が無い結果** → 一時的な失敗として扱い、理由にその旨を付記する。理由: §2.2 の「いずれとも解釈できない形は成功と見なさず一時的な失敗として扱う」に従う。恒久的と決めつけると、通るはずの項目を永久に捨てることになる。
- **上限回数まで試して諦めた理由文** → 送信手段が返した最後の理由に「(一時的な失敗が N 回続いたため、この実行では諦めた)」を付ける。恒久的失敗には付けない。理由: §4.5 が事実と異なる理由を禁じているため、回数を書いてよいのは実際に回数を重ねた場合だけ。
- **待機手段の差し替え** → `options.sleep` で注入できる。理由: 実演・検査で実時間を待たずに「待機が入ったこと」を確かめられるようにするため(§9 の調整値を外から見える形にする方針と同じ趣旨)。
