# 判断の記録

仕様書 `rung1-spec.md` 末尾の「★要確認」は、確認する相手がいないため実装者が判断した。
それ以外に、仕様書が触れていなかったので決めた事柄も併せて残す。

---

## 仕様書の ★要確認

### A. 1 回あたりの上限が数えるもの

**どう決めたか** — 「処理を試みた件数(決着がついた件数)」を数える。成功・恒久的失敗・再送上限到達のいずれでも 1 件消費する。1 件に対する再送は何回行っても 1 件。

**なぜ** — 上限の役割は「1 回の実行の長さ(=外部サービスを叩く量と所要時間)に蓋をすること」だと読んだ。成功件数を上限にすると、全件失敗する日には上限が永遠に埋まらず、実行が並びの最後まで走り切ってしまう。障害中こそ実行が長引くという最悪の形になる。§3 本文も「成功・失敗にかかわらず、決着がついた項目を 1 件と数える」と書いており、本文と現状の実装が一致している以上、これを要件として確定させた。

実装: `lib/sendQueue.js` の `processed += 1`(成功・失敗の分岐の外に置いてある)。

### B. 諦めた項目の扱い

**どう決めたか** — 諦めきる。次回の自動実行(`runBatch`)では拾い直さない。拾い直す手段は `retryFailed`(§8)だけ。

**なぜ** — §5 の不変条件が「一度決着がついた項目(成功・恒久的失敗・再送上限到達のいずれか)は、次回の実行で自動的に再送されてはならない」と明記しており、ここでの選択肢は実質ひとつしかない。自動で拾い直す設計にすると、恒久的失敗の項目を毎回叩き続けることになり、§4.2 の「一切再試行してはならない」と正面から衝突する。運用者の判断を挟む `retryFailed` に一本化した。

実装: `runBatch` は `book.isSettled(id)` が真の位置を、上限を消費せずに読み飛ばす。

### C. 手動再試行の試行回数

**どう決めたか** — 通常の実行と同じ回数(同じ設定値 `maxAttempts`)を使う。手動再試行だけ厚くはしない。ただし呼び出し側が `retryFailed` に別の `maxAttempts` を渡せば、その回だけ変えられる。

**なぜ** — §8 が「通常の実行と同じ規則に従う」と明言している。回数が 3 と 5 で食い違っていたのは、二か所に別々に数字が埋め込まれていた結果と読める(§9 の「コードの中に埋め込んだきりにしない」に反する形)。回数は 1 か所の設定値に集約し、厚くしたい運用があるなら呼び出し時に明示的に指定させる。暗黙に違う回数が走るより、指定が目に見える方が安全。

実装: `resolveConfig` を `runBatch` / `retryFailed` の両方が共有する。

### D. 手動再試行と恒久的失敗

**どう決めたか** — 除外しない。恒久的失敗で諦めた項目も `retryFailed` の対象に含める。ただし送信手段が再び恒久的失敗を返せば、その回も 1 回で諦める。

**なぜ** — 本道具は §2.2 により「一時的か恒久的かの判定は送信手段が下す。本道具が中身を見て推測してはならない」という縛りを負っている。「これは恒久的だったから今回は呼ばない」というのは、過去の判定を本道具が勝手に持ち越して再判定することであり、この縛りを破る。加えて、手動再試行は運用者が「中身を直した」「宛先設定を直した」あとに叩く手段であり、そこで恒久的失敗の項目が対象外だと道具として使えない。一方で「呼んでも通らない」という懸念は、恒久的失敗なら 1 回で終わる(再送しない)ため、コストは 1 件 1 回に収まる。

### E. 待機時間の形

**どう決めたか** — 一定時間の待機のままとする。指数的後退は入れない。待機時間は設定値 `retryDelayMs` で外から変えられ、待機手段そのもの(`wait`)も差し替えられる。

**なぜ** — §4.1 の要求は「待機時間を置くこと。連続で叩き続けてはならない」だけで、間隔の伸び方は要求されていない。既定の再送上限は 3 回、すなわち待機は 1 件あたり最大 2 回しか発生せず、指数的後退が効き始める前に打ち切られる。得られる利益が小さいのに、実際の所要時間の見積もりが難しくなる(§3 の上限が守ろうとしている「1 回の実行の長さ」が読みにくくなる)。伸ばしたい運用が出てきたら、`wait` を差し替えれば呼び出し側で実現できる余地を残した。

実装: `lib/config.js` の `retryDelayMs` と `wait`。

### F. 例外の分類

**どう決めたか** — 例外は一律で一時的な失敗として扱う。例外の型や文言を見て恒久的と判定することはしない。

**なぜ** — D と同じ理由で、§2.2 の「本道具が中身を見て推測してはならない」に従う。例外オブジェクトの中身から恒久性を推し量るのは、まさにその推測にあたる。§4.3 も「一時的な失敗として扱う」と書いている。恒久的だと伝えたい異常があるなら、送信手段の側で捕まえて `{ status: 'permanent', reason }` を返すのが正しい経路であり、そのための境界がすでに用意されている。

**副作用** — 例外を投げ続ける送信手段は 1 件につき `maxAttempts` 回叩かれる(既定 3 回)。これは受け入れる。

実装: `lib/outcome.js` の `fromThrown`。例外の中身(`name: message`)は理由に取り込む。

### G. 「残り件数」の定義

**どう決めたか** — 諦めた項目は残りに含めない。`remaining` は「まだ一度も処理を試みていない項目の数」= `items.length - progress.cursor`。

**なぜ** — §6 本文が既にそう定義しており、B の判断(諦めた項目は自動実行では拾わない)と辻褄が合う。拾わないものを「残り」と呼ぶと、`remaining` が 0 にならないまま実行が何も進まなくなり、「あと何回実行すれば終わるか」を残り件数から読めなくなる。諦めた項目の数は別の口(`failures.length` / `abandoned`)で報告するので、情報は失われない。

実装: 報告に `remaining`(未着手)と `failures`(諦めたまま)を別々に載せた。

### H. 成功した項目の識別値一覧の用途

**どう決めたか** — 件数ではなく識別値の一覧を保持する。

**なぜ** — §5 が「成功した項目の識別値の集合を保持する」と要件として書いている。加えて実装上も必要だった:
1. §5 の「同じ項目を二重に送ってはならない」を、位置(cursor)だけでなく識別値でも守れる(I の保険)。
2. §8 の手動再試行で成功した項目を「諦めた集合から取り除き、成功の記録へ移す」には、成功側が集合でなければ移せない。件数だけでは §8 の「進捗情報は実際の状態と一致していなければならない」を満たせない。
3. 呼び出し側が「何が送れたか」を照合できる。件数だけでは事故の追跡ができない。

### I. 並びの同一性

**どう決めたか** — 再開位置は**位置(cursor)を基準**とする。§5 末尾の「並びの内容が実行間で変わらないことを前提としてよい」に乗る。ただし保険として、位置を進める前に必ず**識別値で決着済みかを照合**し、決着済みなら送らずに読み飛ばす。

**なぜ** — 位置基準にしたのは、識別値基準にすると「未処理の項目を探す」たびに並び全体を走査することになり、また「並びに新しい項目が挿入された/削除された」ときの再開位置の意味が曖昧になるため。仕様が前提を置いてよいと明示している以上、そこに乗るのが素直。

一方で、位置だけを信じると「並びが前にずれた」ときに二重送信が起きる。二重送信は §5 の中でも取り返しがつかない側の事故(外部サービスに実害が出る)なので、識別値による照合を安価な保険として重ねた。並びが変わらない限りこの照合は一度も発火せず、費用はほぼゼロ。

**残る限界** — 並びの**前方**に新しい項目が挿入された場合、その項目は cursor より手前になるため処理されない。これは仕様の前提の外なので、そういう運用が出てきたら再開位置の定義を識別値基準に変える必要がある(その時は `cursor` を捨て、`sent`/`failed` の集合だけで未処理を判定する形になる)。

実装: `runBatch` の `if (book.isSettled(id)) { advance; continue; }`。この読み飛ばしは §3 の上限を消費しない(送信手段を叩いていないため)。

## 仕様書が触れていなかったので決めたこと

### 送信手段が返す結果の形

**どう決めたか** — `{ status: 'success' }` / `{ status: 'temporary', reason }` / `{ status: 'permanent', reason }` の 3 形とした。これ以外の値(`undefined`、`null`、文字列、未知の `status`)はすべて一時的な失敗として扱い、理由に「解釈できなかった」旨と受け取った値を残す。

**なぜ** — 仕様は 3 通りの意味だけを定めていて、形は定めていない。判定を送信手段側に持たせる(§2.2)以上、送信手段が意味を明示的に名乗れる形が要る。真偽値(`ok: true/false`)では「一時的か恒久的か」を言い分けられない。§2.2 末尾の「解釈できない形は成功と見なしてはならない」を守るため、既定を「一時的な失敗」に倒し、未知の形が黙って成功に落ちる経路を作らなかった。

### 進捗情報の形と、更新の伝わり方

**どう決めたか** — 進捗情報は素の JSON オブジェクト(`{version, cursor, sent[], failed[]}`)。`runBatch` / `retryFailed` は**渡された進捗オブジェクトをその場で書き換える**(返り値の `report.progress` も同じオブジェクト)。

**なぜ** — クラスにすると保存・読み戻し(§5 の「呼び出し側はこれを保存し」)に手間がかかる。`JSON.stringify` してそのまま書き戻せる形が一番事故が少ない。
その場で書き換える方を選んだのは、新しいオブジェクトを返す作りだと「返り値を保存し忘れる」だけで二重送信が起きるため。§5 の不変条件のうち二重送信は実害が外に出る事故なので、呼び出し側の記憶に頼らない形にした。

### 識別値が無い項目

**どう決めたか** — 送信を 1 件も始める前に並び全体を検査し、識別値の無い項目があれば `TypeError` を投げて実行しない。

**なぜ** — §9 の「例外を外へ漏らさない」は、処理中(送信手段とのやりとり)に起きた異常についての規律だと読んだ。識別値の欠落は呼び出し側の契約違反であり、進捗の記録も失敗の報告も再試行の対象指定もできない(§2.1)。この状態で送信を始めると、送ったのに記録できない項目が生まれ、二重送信の元になる。送る前に止めるのが最も害が小さい。「一部を送ってから途中で気づく」ことがないよう、検査は先頭で一括して行う。

### 手動再試行で、並びの中に見つからない項目

**どう決めたか** — 送信手段を呼ばず、諦めたまま理由も変えずに残す。`attempted` にも数えない。

**なぜ** — 送るべき中身が手元にないので、送りようがない。黙って失敗集合から消すと §8 の「進捗情報は実際の状態と一致していなければならない」に反する(送れていないのに記録から消える)。試していないものを「試した件数」に数えるのも報告として嘘になる。

### 完了の報告

**どう決めたか** — `complete`(全件に決着がついたか)と `clean`(諦めた項目がゼロか)の 2 つを別々に返す。補助として `isComplete()` / `isCompleteAndClean()` も公開した。

**なぜ** — §7 が「『全件処理済み』と『失敗ゼロ』は別の概念として扱える」ことを要求している。1 つの真偽値に畳むとこの区別が失われる。
