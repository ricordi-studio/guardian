# EXP-004 結果 ── 足りなかったのは【問いの種類】ではなく【運用の文脈】だった

題材: 台帳に従ってファイルを配布先へ写す道具(80行)。
**これまでと決定的に違う点: 仕込んだ壊れ6件が、すべて「無いもの」。**
コードは短く、重複が無く、名前も素直で、**見て変な所が1つも無い。**

## 3通りの問いで測った

| | N1 全か無か | N2 パス検証 | N6 確認・退避 | N3 上限 | N4 錠 | N5 記録 |
|---|---|---|---|---|---|---|
| **段0**「一から書くなら?」 | ✓ | ✓ | ✓ | ✗ | ✗ | ✗ |
| **変種**「何が起きたら困る?」 | ✓ | ✓ | ✓ | ✗ | ✗ | ✗ |
| **段0 + 運用の文脈4行** | ✓ | ✓ | △ | **✓** | **✓** | **✓** |

★**問いを変えても、見える範囲は1ミリも動かなかった。**(段0と変種が同じ3件を見つけ、同じ3件を見逃した)
★**問いを変えず、文脈だけ足したら、動いた。**

## 足した文脈と、出てきたものが1対1で対応した

| 足した文脈(4行) | 出てきたもの |
|---|---|
| 数百MBの資料がある | **N3** ── 常駐メモリが原本の3〜4倍 / **V8の文字列長上限で `ERR_STRING_TOO_LONG`**、しかもそれが `catch` に飲まれて「1件失敗」としか出ない |
| cronで5分ごと・手でも叩く | **N4** ── 1回が5分を超えたら**前回と次回が同じファイルに同時に書く**。後発は「実行中」と言って正常終了させる |
| 5人が編集・2年運用 | **N5** ── **2年回すログに時刻もホストも実行IDも無い**。「このファイルはいつ差し替わったのか」を後から答えられない |

## ★第3の可能性(文脈は心配性にするだけ)は否定された

回す前に反証条件として書いておいた ──「文脈と無関係なものまで大量に出たら、
文脈は判断を精密にするのではなく不安を膨らませるだけ」。

**起きなかった。むしろ逆だった:**

> この道具は**「小さなテキストを、自分1人が、手で、閉じた場所へ写す」という前提でなら妥当な形をしています。**

**批判の範囲を、文脈に合わせて絞っている。** 文脈が無ければ「欠陥」ではないことを、明示的に述べた。

さらに11項目を**3つの層**に畳み、それぞれを文脈の事実に紐づけた:

1. **台帳を「信頼できない入力」として扱う層** ← 5人が編集する
2. **配布先を「公開中の資産」として扱う層** ← 社外に公開される
3. **無人で回り続ける前提の層** ← cronで5分ごと・2年

**文脈の4行が、3つの層に変換された。**

## 独立に到達したもの(教えていない)

> 壊れたエントリが1件あると**5分ごとに非ゼロ終了 = 1日288通の通知**が2年続く。
> そうなった通知は必ず無視されるので、**同じ失敗を繰り返している間は通知しない**設計が要る。

これは Guardian の RULES 7条「催促は『出し過ぎない』ことまで含めて設計する」と同じ結論。
**規律を教えなくても、文脈さえあれば同じ所に着いた。**

他に仕込んでいないもの: Shift_JIS の文書が静かに壊れる / 単独CRが残る(宣言と実装の不一致) /
`HEADER` が冪等でない / 終了コードが「引数不足」と「1件失敗」を区別しない /
**エラー報告の最中に例外で落ちる**(`f.entry` が null のとき)。

## 結論

> **足りなかったのは【問いの種類】ではなく、【運用の文脈】という入力だった。**

問いを増やせば門が増える(帰納法の罠)。**文脈を渡すのは、入力を1つ足すだけ。**

そしてこれは、この日に逆算した機構と一致する ──
**目的と運用の文脈が与えられれば、幅も深さも備えも降りてくる。**
与えられなければ誰も決められない ── そして**決めなかったエージェントは正しかった。**
「錠が無い」は、同時に走る運用でなければ欠陥ではない。
